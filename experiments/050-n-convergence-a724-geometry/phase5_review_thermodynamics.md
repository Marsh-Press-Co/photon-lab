## (a) Cost/runtime accounting — the memoization attribution is PLAUSIBLE IN DIRECTION but the docstring's own reasoning for skipping the fix does not hold up

NOTES.md's Results section attributes the ~15% runtime overrun (6225.3s vs.
the ≈90-minute/5400s estimate) to "the new geometry-parameterized functions'
lack of a `_Gcache`-style memoization (disclosed as a known cost gap in
`design_geometry.py`'s own `_G_for_g` docstring)." I read that docstring
directly (`design_geometry.py:67-79`):

> "No caching (unlike exp-042's own `_Gcache`) -- this module is called far
> fewer times per geometry than exp-042's own dense theta sweep needed."

**Direction: correct — a cache would have removed real, verified redundant
work.** `_geom_derived(g)` (`experiments/048-.../design_geometry.py:179-197`,
reused unmodified) is called once per `beam_divergence_*` invocation
(`design_geometry.py:96,118,134`) and builds a full `(N,N)` dense matrix
(`r = sqrt(d_sp²+dy²)`, `obliquity = d_sp/r`, `N = NY-2·ABSORB` = 1448 at
GEOM78 / 1504 at GEOM_EXP042_OLD — ≈2.1–2.3M elements) **from scratch every
call**, even though `g` (and therefore `r`/`obliquity`) is bit-identical
across every one of the 972 calls that share a geometry (36 cells × 3
functions × 9 n-values, verified directly against `run.py:44-45,93-110` and
`CELLS`/`FUNCS`/`N_SERIES`+regression counts). `_G_for_g` compounds this
with its own fresh `G0` build on top. Total: 1944 full matrix rebuilds
across the run (972 × 2 geometries) — a genuinely large, avoidable cost
(order 4×10⁹ elementwise ops for the `r`/`obliquity` matrices alone).

**But the docstring's own stated justification for skipping the cache is
false, checked directly, not merely doubted.** I compared call counts: I
read `experiments/049-.../run.py:148,151` — exp-042's own module-global
`beam_divergence_*` functions are called with the **identical** loop
structure (36 cells × 3 functions × 9 n-values = 972 calls) in exp-049's own
sweep, at a **single** geometry. That is not "far fewer" than this module's
972-calls-per-geometry — it is the same number. The real reason exp-042's
version was fast is not call frequency, it is that its geometry matrices
(`_R`, `_OBLIQUITY`) are **module-level globals, built exactly once at
import** (`experiments/042-.../design_geometry.py:180-190`-adjacent), never
rebuilt regardless of how many times `_G_for` is called — `_Gcache` itself
only additionally saves the propagator-matrix step on top of that. exp-050's
`_geom_derived(g)` reintroduces, at the *geometry* layer, precisely the
"wasteful... original prototype's own performance bug" `_Gcache`'s own
docstring (`experiments/042-.../design_geometry.py:200-204`) says was
already fixed once in this program's history — now for a second, larger
matrix. **Verdict: the attribution ("lack of memoization caused the
overrun") is correct; the code's own stated reason ("called far fewer
times") is not — the actual story is a same-count-but-uncached repeat of a
bug this program already named and fixed once, at a different layer.** Not
disclosed anywhere as such — NOTES.md's one-line attribution doesn't
distinguish "fewer calls, so it doesn't matter" (the docstring's claim, now
shown wrong) from "same call count, no cache, real waste" (what actually
happened).

## (b) Reproducibility/provenance rigor — the runtime figure reported for this cycle is very likely only HALF the true cost incurred, undisclosed

NOTES.md: *"One implementation bug self-caught before any result was
produced: the first execution crashed with `KeyError: 'n401'`... Fixed
pre-result (no science number was ever generated by the buggy version);
full sweep re-run clean."*

This is **literally true and honestly framed as far as it goes** — I
confirmed via `git show dc7170f` that the bug is exactly what's described
(`run.py`'s regression-anchor loop compared `d["n401"]` against
`row049["n401"]`, but exp-049's own committed `results.json` uses the field
name `c401`, not `n401` — a `KeyError` on lookup, not a wrong number). No
`results.json` was ever written by the buggy run (confirmed: the crash site,
line ~144 in the pre-fix code, sits *after* both `sweep()` calls but
*before* `json.dump`, per `run.py`'s current structure at
lines 116-118/319-321 — the write only happens at the very end).

**But "no science number was ever generated" silently elides that the
buggy run still had to pay almost the entire compute cost before it
crashed** — `sweep()` runs both geometries (all 1944 records / the whole
expensive matrix-rebuild workload documented in §(a) above) *before*
reaching the comparison loop that crashed. That means the first, discarded
execution very likely cost close to the same wall-clock time as the second,
reported one — and NOTES.md's "6225.3s (103m45s), about 15% over the
≈90-minute estimate" describes **only the second run**, with no mention that
a first, comparably expensive run preceded it.

I checked this is not merely a structural possibility but a real
computational fact, from `git log` timestamps (not asserted from memory,
per this program's own R4 rule):

| Commit | Timestamp | Gap to next |
|---|---|---|
| `3139376` (implementation committed — the buggy code) | 09:47:07 | |
| `dc7170f` (bugfix: `n401`→`c401`) | 11:31:54 | **1h44m47s (6287s)** |
| `291c6dd` (results committed) | 13:15:17 | **1h43m23s (6203s)** |

The second gap (6203s) matches `results.json`'s own reported
`elapsed_s=6225.346` almost exactly (the ~22s difference is ordinary
commit/write overhead) — confirming that field measures only the clean,
post-fix run. **The first gap is essentially the same size (6287s vs.
6203s)** — strong circumstantial evidence that the crashed run's own
`sweep()` calls (which must complete in full, at both geometries, before
the crash site is even reached) consumed a comparable ~1h44m of wall-clock
time, silently absent from every cost figure this cycle discloses. I flag
this as a well-evidenced inference from git provenance, not a certainty (no
direct stdout/log of the first run survives to confirm it directly) — but
it is the natural reading of the code's own control flow plus the matching
timestamps, and no weaker explanation (e.g., "1h45m of pure debugging with
no run at all") is consistent with a bug that only manifests after the full
sweep completes.

**Reading NOTES.md's "about 15% over the ≈90-minute estimate" as this
cycle's true cost is very likely an underestimate by roughly 2×** (nearer
~200 minutes of actual compute against a 90-minute estimate) — not a false
statement about what `elapsed_s` measures, but an incomplete provenance
disclosure of what the cycle actually cost, in exactly the discipline
(cost/runtime accounting) my own Iteration-26 critique flagged for a
smaller (0.03pp) arithmetic slip. This is the kind of gap this program's own
R4 rule and its fix-docket-delivery pattern (LOGBOOK, Iterations 13-15,
17, 20-23, 25, 26) exists to catch — non-load-bearing to any of the eight
scored predictions (none depend on wall-clock time), but a real,
correctable disclosure gap in exactly the ledger my seat owns.
